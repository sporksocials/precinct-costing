# Precinct Costing — Claude Code guide

Recipe costing app for the Caloundra Food Precinct (Drift Bar, Chiobu, Greedy Gringo's, Gelato Rumba), built by SPORK Socials for Troy.
Live: https://precinct-costing.vercel.app — pushes to `main` auto-deploy on Vercel (project `precinct-costing`, team sporksocials-projects).

## How to work here
- Act as the orchestrator. Split any job with independent parts across parallel subagents (use worktrees when they touch different files), then review, merge, and run the checks below yourself before committing.
- Make and own design calls; say what you decided and why. Don't ship something and wait for Troy to spot problems, and don't reply "I agree" to a flaw you introduced — fix it.
- Before every commit: `npx tsc --noEmit`, `npm test` (vitest), `npm run build`. For UI changes, design and check BOTH phone (390px) and desktop widths every time, including small requests and subagent briefs; never ship one and leave the other behind (Troy's standing rule).
- Commit and push to `main` when the checks pass, then confirm the Vercel deploy is READY.
- Keep the repo clean: no scratch files, screenshots or exports committed.
- **Where files live:** every file we create or receive for this project (client workbooks, source spreadsheets, exports, research, scripts, analysis) lives in `files/` inside this folder, and nowhere else (not `~/SPORK`, not a `Claude outputs` folder, not Downloads copies). `files/` is gitignored because the repo is public and the files hold client pricing. Layout: `files/client-sent/` (what went to the client, dated), `files/source/` (originals still needed), `files/research/`, `files/archive/<date>-<topic>/` (finished work kept for the record). Session scratch goes in the session scratchpad and is not kept.
- **Always clean up:** when a file is superseded or a task is finished, remove it in the same session: move working copies to the macOS Trash (recoverable), keep only the final version in `client-sent/`, archive scripts and analysis worth keeping under `archive/`, and delete the rest. Never leave duplicate copies (top-level, outputs folders, Downloads). Delete finished agent worktrees and their merged branches (`git worktree remove --force <path>`, `git branch -d <branch>`) after merging. Never touch the client's original files in Downloads.
- **Push check:** `git config core.hooksPath .githooks` (once per clone) enables `.githooks/pre-push`, which blocks a push when tracked files have uncommitted changes, the type check fails, or tests fail (`PREPUSH_BUILD=1` adds the build). Vercel builds whatever is committed, so never push without it.

## Hard rules
- **Never commit or deploy `.demo/`** (local QA fixture containing client pricing). Never set `NEXT_PUBLIC_DEMO` on Vercel.
- Never store supplier-portal credentials anywhere; never type passwords into forms.
- Database: Supabase project `precinct-costing`, ref `epktnpxjlkweyozpsvyr` (Sydney). Only use this project. Do NOT touch the `spork-ops` project (nagspgiqaenrzftmjejk) or its Site URL.
- Before any bulk data change: back up the affected tables into the `backup` schema (`backup.<table>_<yyyymmdd>`). Delete data only with Troy's explicit OK.
- Schema changes: apply as a migration AND mirror them in `supabase/schema.sql`. All `cost_*` tables use RLS via `cost_is_allowed()` (emails in `cost_allowed_users`).
- **Every insert goes through `insertRow`/`insertRows` in `lib/store.tsx`, never `sb.from(table).insert(...)` directly.** They strip null/undefined keys before sending, so a NOT NULL column with a server-side default (category, venues, and others — see `withoutNulls`'s doc comment) gets that default instead of a hard failure. This bit twice on cost_ingredients (category, then venues) before the guard existed; don't reintroduce a raw `.insert(`. When auditing "could this field ever be null", check the LIVE database's `information_schema.columns` (`is_nullable`, `column_default`), not just `supabase/schema.sql` — that file has drifted from production before.

## Stack
Next.js 14 (app router, client components + `lib/store.tsx` global store), Tailwind, Supabase JS, lucide-react, vitest.
- `lib/costing.ts` — cost, GP, target resolution, suggested price. Costs ex GST, sell prices inc GST. Suggested price = cost ÷ (1 − target) × 1.1, rounded UP to 20c (`settings.round_to`).
- `lib/gelato.ts` — gelato: flavour = mix prep × `cost_gelato_serves`; virtual items `gelato~<prepId>~<serveId>`. Wastage setting `gelato_wastage`.
- `lib/beer.ts` — tap beer: beer = one keg × `cost_beer_serves` (Pot 285 / Schooner 425 / Pint 570 / Jug 1140 ml); prices in `cost_beer_prices`; virtual items `beer~<beerId>~<serveId>`. **Wastage lives on each keg ingredient's yield** (Troy's decision) — don't add serve-level wastage.
- Virtual items are computed, never stored. Old stored items they replace are hidden via `replacedItemIds` / `legacy_item_id` (297 gelato items still in the DB awaiting Troy's OK to delete; the 116 old tap beer items were set not active on 4 Oct 2026).
- `lib/insights.ts` — Today feed: price rises, below target, stale prices (90 days), catalogue gaps.
- `components/ui.tsx` — design primitives (PageHeader, Group, Row, FieldRow, InlineInput, Sheet, Chips, AddButton, Toggle…). Reuse them; don't invent new one-off styles.
- Information architecture: every kind of thing has one home. **Menu** (`app/(app)/menu`) lists everything sold (food, drinks, tap beer rows, gelato flavours); venue tiles and category chips only filter it. **Ingredients** has an Ingredients | Preps control (`?type=preps`). Tap beer detail is `/beers/[id]`, gelato Price Grid `/gelato`, serves `/gelato/serves`; old `/recipes`, `/beers`, `/items`, `/preps` redirect (next.config.mjs).
- **Download POS List** (`components/pos-list-button.tsx` on the Menu page under the venue tiles, `lib/pos-list.ts` pure rows, `lib/pos-list-xlsx.ts` workbook, `tests/pos-list.test.ts`, `tests/pos-list-xlsx.test.ts`): one quiet plain button (44px, "Preparing..." then a toast) that downloads an Excel file for the venue chosen above (All = one file, one tab per venue, plus a Notes tab) for keying or importing the menu into the till (Toast at Chiobu). No schema, no writes, no costs, GP or targets in the file; it is worked out from the store. Columns: Menu Group, Item, POS Button Name, Size / Option, Price inc GST, Price ex GST (a real formula off the GST rate cell G2, from `gst_rate`), Happy Hour inc GST, Notes. Active items only; item names in Title Case (spelling untouched); group is the item's `section`, else by category (Cocktails, Mocktails, Wine, Soft Drinks for Cold Drink, Food, Tap Beer); wine and soft drink items are split on the LAST " - " into item and size (never for Food, Cocktail, Mocktail); tap beers and gelato come from the beer and serve tables (one row per size or serve, gelato serves that are on the menu, never flavours). The button name is generated, 19 characters or fewer, never stored (`buttonName`: "and" to "&", drop "The", drop a trailing count, drop Chicken or Salad only if still too long, abbreviate known long words, cut at a word boundary); a row with no price or a name that cannot fit is yellow with a note. The item's own `notes` appear only when short and plain (`plainNote`). The Excel library and `lib/pos-list.ts` are loaded by dynamic `import()` inside the click handler so they stay out of the Menu page bundle; use exceljs, not SheetJS. Tab names and file names (`<Venue> POS List (<d Mmm yyyy>).xlsx`, Brisbane date) come from `posFileName` and `sheetTabName`. The Notes tab names no POS vendor menu paths (unverified).

- **Recipe editor is manual-save with a leave guard** (`components/editor/recipe-editor.tsx`, `components/save-bar.tsx`, `components/unsaved-guard.tsx`, `lib/unsaved-guard.ts`, `lib/draft-changes.ts`): edits stay in a draft until the person taps Save in the bottom save bar (Discard shows "Discard N Changes?" first). - **Full change history** (`cost_change_history`, migration `20261004240000_change_history.sql`, mirrored in `supabase/schema.sql`; `lib/change-history.ts`; Change Log page `app/(app)/change-log`): one generic trigger `cost_history_log()` writes a row (whole `old_row` and `new_row`, `changed_fields`, parent table and id for child rows, `tx_id`) for every insert, update and delete on: menu items, preps, recipe lines, ingredients, beers, beer serves and prices, gelato serves and lines, offers and lines, ingredient deals, suppliers, specials, targets, settings, glass and rim options and the sign-in list. NOT tracked: the three log tables, `cost_portal_prices` (bulk imports), research notes, ignored alerts, venues. Bookkeeping columns (`updated_at`, `updated_by`, `created_at`, `sort`) never count: an update that changes only those writes nothing, so recipe saves (delete removed lines, upsert all) and the edit stamp triggers add no noise. `changed_by` is the signed-in email; **null means direct database work** (SQL editor, migrations, service role) and the page shows it as "System". The function never fails the business write (it warns and returns). The table is read only for allowed users (select policy only; only the definer trigger writes). The Change Log merges it with the older logs and hides history events they already report (sell and happy hour price, ingredient priced fields, active and own target, and everything the audit log keeps for targets, settings and sign-ins); child rows of a deleted or just created record fold into that one event. Part 2 (Trash, restore, Undo This Change) builds on `old_row` and `parent_table`/`parent_id`. Demo mode synthesises history rows in memory (`lib/supabase/demo-client.ts`).

No near match is silence, so new words (Karaage, Hiramasa) are never flagged. **3 Smart check** (`/api/name-check`, signed in and allow-listed only, same pattern as the allergen route): a small fast model (`NAME_CHECK_MODEL`, default `claude-haiku-4-5-20251001`) gets the tidied name, its kind (menu_item, drink, ingredient, prep, beer) and up to 150 known words (those nearest the unknown typed words first) and answers `{"corrected","changed","reason"}`. The reply is REJECTED, meaning no suggestion, when it is not that JSON, the name or the reason is over 80 characters, either holds an em or en dash, or it changes more than spelling and capitals (`onlySpellingChanged`: same number of words in the same order, each word the same or within 1 edit (2 for 5 or more letters), 4 edits in all, numbers and symbols untouched). The route and the browser (`createNameChecker`: debounced 1 s, asks only for a tidied text it has not answered, caches every answer by exact text and kind, gives up after 6 s, stops after a 401 or three failures, never more than 40 asks per mounted field) both run the checks; there is no AI fallback to build and failure is silent. The key is read server side from `ANTHROPIC_API_KEY` only (`ANTHROPIC_BASE_URL` for tests), never returned or logged. **UI**: a quiet row under the field, "Did you mean <name>?" with 44px "Use It" and "Keep Mine" (own button classes: the shared `.btn` shrinks at `sm:`). Keep Mine dismisses that text and those words for the session. Only layer 1 is automatic; layers 2 and 3 never apply without a tap, never block Save, one suggestion at a time (the smart one replaces the vocabulary one), shown only after the person has changed the name. The hook changes the field through `setValue` exactly like typing (the recipe editor passes a `setDraft`, so the Save bar, leave guard and conflict check apply) and never writes to the database; the vocabulary and smart-check code load lazily (dynamic import) on the first changed name. **Where it applies:** New Menu Item and New Prep (`components/new-recipe.tsx`), New Gelato Flavour, the name in the recipe editor (items, drinks, preps), New Ingredient (`components/ingredient-sheet.tsx`) and the ingredient Name under Advanced, New Tap Beer (`components/beer-parts.tsx`) and the tap beer Name. No existing data is changed in bulk.
