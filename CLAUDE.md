# Precinct Costing — Claude Code guide

Recipe costing app for the Caloundra Food Precinct (Drift Bar, Chiobu, Greedy Gringo's, Gelato Rumba), built by SPORK Socials for Troy.
Live: https://precinct-costing.vercel.app — pushes to `main` auto-deploy on Vercel (project `precinct-costing`, team sporksocials-projects).

## How to work here
- Act as the orchestrator. Split any job with independent parts across parallel subagents (use worktrees when they touch different files), then review, merge, and run the checks below yourself before committing.
- Make and own design calls; say what you decided and why. Don't ship something and wait for Troy to spot problems, and don't reply "I agree" to a flaw you introduced — fix it.
- Before every commit: `npx tsc --noEmit`, `npm test` (vitest), `npm run build`. For UI changes, design and check BOTH phone (390px) and desktop widths every time, including small requests and subagent briefs; never ship one and leave the other behind (Troy's standing rule).
- Commit and push to `main` when the checks pass, then confirm the Vercel deploy is READY.
- Keep the repo clean: no scratch files, screenshots or exports committed.
- **Where files live:** every file we create or receive for this project (client workbooks, source spreadsheets, exports, research, scripts, analysis) lives in `files/` inside this folder, and nowhere else (not `~/SPORK`, not a `Claude outputs` folder, not Downloads copies). `files/` is gitignored because the repo is public and the files hold client pricing. Layout: `files/client-sent/` (what went to the client, dated), `files/source/` (originals still needed), `files/research/`, `files/archive/<date>-<topic>/` (finished work kept for the record). Session scratch goes in the session scratchpad and is not kept.
- **Always clean up:** when a file is superseded or a task is finished, remove it in the same session: move working copies to the macOS Trash (recoverable), keep only the final version in `client-sent/`, archive scripts and analysis worth keeping under `archive/`, and delete the rest. Never leave duplicate copies (top-level, outputs folders, Downloads). Delete finished agent worktrees and their merged branches (`git worktree remove --force <path>`, `git branch -d <branch>`) after merging. Never touch the client's original files in Downloads.
- **Push check:** `git config core.hooksPath .githooks` (once per clone) enables `.githooks/pre-push`, which blocks a push when tracked files have uncommitted changes, the type check fails, or tests fail (`PREPUSH_BUILD=1` adds the build). Vercel builds whatever is committed, so never push without it.

## Hard rules
- **Never commit or deploy `.demo/`** (local QA fixture containing client pricing). Never set `NEXT_PUBLIC_DEMO` on Vercel.
- Never store supplier-portal credentials anywhere; never type passwords into forms.
- Database: Supabase project `precinct-costing`, ref `epktnpxjlkweyozpsvyr` (Sydney). Only use this project. Do NOT touch the `spork-ops` project (nagspgiqaenrzftmjejk) or its Site URL.
- Before any bulk data change: back up the affected tables into the `backup` schema (`backup.<table>_<yyyymmdd>`). Delete data only with Troy's explicit OK.
- Schema changes: apply as a migration AND mirror them in `supabase/schema.sql`. All `cost_*` tables use RLS via `cost_is_allowed()` (emails in `cost_allowed_users`).
- **Every insert goes through `insertRow`/`insertRows` in `lib/store.tsx`, never `sb.from(table).insert(...)` directly.** They strip null/undefined keys before sending, so a NOT NULL column with a server-side default (category, venues, and others — see `withoutNulls`'s doc comment) gets that default instead of a hard failure. This bit twice on cost_ingredients (category, then venues) before the guard existed; don't reintroduce a raw `.insert(`. When auditing "could this field ever be null", check the LIVE database's `information_schema.columns` (`is_nullable`, `column_default`), not just `supabase/schema.sql` — that file has drifted from production before.

## Stack
Next.js 14 (app router, client components + `lib/store.tsx` global store), Tailwind, Supabase JS, lucide-react, vitest.
- `lib/costing.ts` — cost, GP, target resolution, suggested price. Costs ex GST, sell prices inc GST. Suggested price = cost ÷ (1 − target) × 1.1, rounded UP to 20c (`settings.round_to`).
- `lib/gelato.ts` — gelato: flavour = mix prep × `cost_gelato_serves`; virtual items `gelato~<prepId>~<serveId>`. Wastage setting `gelato_wastage`.
- `lib/beer.ts` — tap beer: beer = one keg × `cost_beer_serves` (Pot 285 / Schooner 425 / Pint 570 / Jug 1140 ml); prices in `cost_beer_prices`; virtual items `beer~<beerId>~<serveId>`. **Wastage lives on each keg ingredient's yield** (Troy's decision) — don't add serve-level wastage.
- Virtual items are computed, never stored. Old stored items they replace are hidden via `replacedItemIds` / `legacy_item_id` (297 gelato items still in the DB awaiting Troy's OK to delete; the 116 old tap beer items were set not active on 4 Oct 2026).
- `lib/insights.ts` — Today feed: price rises, below target, stale prices (90 days), catalogue gaps.
- `components/ui.tsx` — design primitives (PageHeader, Group, Row, FieldRow, InlineInput, Sheet, Chips, AddButton, Toggle…). Reuse them; don't invent new one-off styles.
- Information architecture: every kind of thing has one home. **Menu** (`app/(app)/menu`) lists everything sold (food, drinks, tap beer rows, gelato flavours); venue tiles and category chips only filter it. **Ingredients** has an Ingredients | Preps control (`?type=preps`). Tap beer detail is `/beers/[id]`, gelato Price Grid `/gelato`, serves `/gelato/serves`; old `/recipes`, `/beers`, `/items`, `/preps` redirect (next.config.mjs).
- **Drinks Station** (the public iPad screen at `/bar/<venue>`; the code and routes keep the name "bar": `lib/bar.ts`, `components/bar/`, `cost_bar_menu`; it used to be called the Cocktail Station) carries Cocktails, Mocktails and Cold Drinks (`BAR_CATEGORIES`). **Cold Drink** is a `cost_menu_items.category` value (singular in data, "Cold Drinks" on the chip) for Drift's smoothies, iced coffees, frappes, milkshakes and spiders: a drink for every rule (no menu labels, drinks side of the GP split, `DRINK_CATEGORIES`), the same glass-and-method rule to show on the station, no Research This Drink, and no shots on its card (milk reads "90ml", not "3 shots"; `usesShots`, scoop and pump amounts read as words). The station's chips (`barChips`) are All plus one per category the venue actually has, and no chips when there is only one. The editor switch reads "Show On Drinks Station" and the detail screen's back bar "Back To All Drinks". A new category value needs: `MENU_CATEGORIES`, `DRINK_CATEGORIES` (`lib/insights.ts`, `lib/trash.ts`, `lib/change-history.ts`), the New Recipe keyword guess, and the category lists inside `cost_bar_menu` / `cost_bar_premix` (migration `20261005200000_bar_menu_cold_drinks.sql`). Target GP for a missing (venue, category) row falls back to the 72% default.
- The **Drinks Station** (above) and **Kitchen Station** (`/kitchen/<venue>`, `lib/kitchen.ts`, `lib/kitchen-model.ts`, `components/kitchen/`): public no-login iPad screens (login bypass in `middleware.ts`). Data comes only from the narrow SECURITY DEFINER functions `cost_bar_menu` / `cost_kitchen_data` (display fields, never prices); both stations share `lib/sw-source.ts` (offline service worker, separate scopes) and the `bar-photos` storage bucket (`/bar/photo`, `/kitchen/photo` rewrites). Kitchen content is gated per record by `kitchen_ready` (the head chef's "Ready For Kitchen" switch in the recipe editor); allergens come from `lib/allergens.ts` and an unreviewed ingredient never reads as "free from". Add a kitchen venue in `KITCHEN_VENUES` (Drift only for now). Edits reach the iPads within 5 minutes; there is no publish step.
- `components/venue.tsx` — VenueFilter (five separate tiles: All / Drift / Chiobu / Greedy / Gelato; selected tile fills with the venue colour and a tick) sits on Home, Menu, Ingredients > Preps and Specials; the choice lives in `?venue=` (no storage, default All) and the accent follows it only on those pages. Targets in the DB stay at 72% everywhere (Troy's call). Record pages use `VenueAccent` (the record's own venue); everything else is neutral sand.
- **Home and /alerts** (`app/(app)/page.tsx`, `components/dashboard.tsx`, `lib/dashboard.ts`; the full feed is `components/today-feed.tsx`, hosted by `app/(app)/alerts/page.tsx`): Troy's brief (5 Oct 2026): first a busy tile dashboard was "overwhelming, too many colours", then plain was "not visual enough". The settled design: Home is ALWAYS all venues with NO venue buttons or tiles. Only THREE colours carry meaning: green (at or over target, "On Target", Check), amber (within 3 points under, "Nearly There", Target icon; `NEARLY_PTS` in lib/dashboard.ts) and red (further under, "Below Target", TrendingDown); no venue colours, no coloured pills, and every colour is backed by a word and an icon. Hero card: the date, the Average GP in big green or red type with a matching glow and a count-up, the status word with the gap in points, a slider (`Slider` in the component: the TARGET is the tick in the middle of the track and the scale runs 25 points either side, `sliderPos` / `SLIDER_HALF` in lib/dashboard.ts, so the bar shows how far over or under you are; the fill slides out from empty on load and a knob rides its end) and a motivating line ("Closest to target: Drift, 4 points to go.", or "Every venue is on target. Nice work."). Venues card: one tappable row per venue (opens `/menu?venue=<slug>`) with its GP in its status colour and its own slider (staggered slide). Then Needs Attention (top 3 on phones, 5 from md up via CSS `hidden md:block`, header total, red gap numbers, "View All N" to `/alerts`, no Ignore button on Home) and two quiet link rows (Specials, Data Health, plus Ignored Alerts when any). Motion respects reduced motion (`motion-reduce:transition-none`, count-up static). Needs Attention ranks every OPEN alert (`rankAttention`, tiers in `TIER`). `/alerts` is the complete Today feed (all grouped lists, Open | Ignored, Review & Apply, Show All) with a BackLink to Home, the venue tiles and `?venue=` carried over, anchors `#below-target`, `#price-rises`, `#missing-price`, `#check-cost`; Home stays highlighted in the nav on `/alerts`. Every count comes from `useOpenAlerts(venueId)` (one hook, ignored alerts already taken out), so a Home number always equals the list behind it; never count alerts any other way. Pure helpers and tests: `lib/dashboard.ts`, `tests/dashboard.test.ts` (some helpers there are no longer used by Home). Do not add tiles, more colours or charts to Home without asking Troy.
- **Recipe editor is manual-save with a leave guard** (`components/editor/recipe-editor.tsx`, `components/save-bar.tsx`, `components/unsaved-guard.tsx`, `lib/unsaved-guard.ts`, `lib/draft-changes.ts`): edits stay in a draft until the person taps Save in the bottom save bar (Discard shows "Discard N Changes?" first). While the draft differs from the saved record, `useUnsavedGuard(dirty, { save })` asks "Unsaved Changes" (Save And Leave / Leave Without Saving / Keep Editing) on link clicks, Back, tab close and reload; any code that calls `router.push` from a page that can hold edits must use `useGuardedRouter()`, not `useRouter()`. `OfferBuilder` uses the same hook; every other page saves per field and needs no guard.
- **Full change history** (`cost_change_history`, migration `20261004240000_change_history.sql`, mirrored in `supabase/schema.sql`; `lib/change-history.ts`; Change Log page `app/(app)/change-log`): one generic trigger `cost_history_log()` writes a row (whole `old_row` and `new_row`, `changed_fields`, parent table and id for child rows, `tx_id`) for every insert, update and delete on: menu items, preps, recipe lines, ingredients, beers, beer serves and prices, gelato serves and lines, offers and lines, ingredient deals, suppliers, specials, targets, settings, glass and rim options and the sign-in list. NOT tracked: the three log tables, `cost_portal_prices` (bulk imports), research notes, ignored alerts, venues. Bookkeeping columns (`updated_at`, `updated_by`, `created_at`, `sort`) never count: an update that changes only those writes nothing, so recipe saves (delete removed lines, upsert all) and the edit stamp triggers add no noise. `changed_by` is the signed-in email; **null means direct database work** (SQL editor, migrations, service role) and the page shows it as "System". The function never fails the business write (it warns and returns). The table is read only for allowed users (select policy only; only the definer trigger writes). The Change Log merges it with the older logs and hides history events they already report (sell and happy hour price, ingredient priced fields, active and own target, and everything the audit log keeps for targets, settings and sign-ins); child rows of a deleted or just created record fold into that one event. Part 2 (Trash, restore, Undo This Change) builds on `old_row` and `parent_table`/`parent_id`. Demo mode synthesises history rows in memory (`lib/supabase/demo-client.ts`).
- **History on every record page** (`components/editor/record-history.tsx`, `lib/record-created.ts`): one `RecordHistory` group `(table, rowKey, label)` on dishes, drinks, preps, ingredients, tap beers, gelato serves, offers and (embedded under "Show History") ingredient deals. It always starts with "Created by <name>, <date>" from the earliest insert row in `cost_change_history`, or "Created <date>. Who created it was not recorded." from `created_at` for records older than the history (5 Oct 2026), then "Last changed by ...", then the latest events for the record and its child rows (registry in `lib/trash.ts`). Read only; Undo This Change exists only via the `undo` option on dishes, drinks and preps. A new record type needs `STAMP_COLUMNS` in `lib/record-created.ts` and the group on its page (`tests/record-history-pages.test.ts` lists the pages).
- **Research Notes apply** (`lib/research-notes.ts`, `components/editor/research-notes.tsx`): Approve on a note with priced `changes`, a `method_step` or an `answer_prompt` first shows a one-tap preview of exactly what changes, then writes it (on the recipe page through the editor draft, then an immediate save of everything pending; on `/research-notes` through the store) and records `applied` on the note for Undo / Undo And Reopen. Prep notes and notes with nothing to apply just close.
- **Ignored alerts** (`lib/ignored-alerts.ts`, `components/alert-parts.tsx`, table `cost_ignored_alerts`, shared by everyone who can sign in): every Today alert row has an Ignore button (Undo toast) and Today has an Open | Ignored (n) control (`?alerts=ignored`) listing what was ignored, who and when, each with Restore. `alert_key` is the kind, the thing and the state it was raised in (price rise: the price log row; below target and happy hour: the price), so a changed situation shows again; ignored alerts never count in Home or venue-tile counts. Counts and filters go through `openRows`; a new alert kind needs its key and entry builder there.
- **Method step tidy** (`lib/method-style.ts` built-in engine, `lib/method-assist.ts` + `app/api/method-assist/route.ts` smart path, `lib/method-assist-client.ts`): the suggested or typed step is tidied into the house style and placed by stage; the route is signed-in and allow-listed only. With no key everything runs through the built-in engine. Env vars (all optional, set by Troy in the Vercel project settings; never written to disk or the repo, never read or printed in a session):
  - `ANTHROPIC_API_KEY`: turns on the smarter tidy. Without it the built-in engine answers.
  - `METHOD_ASSIST_MODEL`: model for the tidy (default `claude-sonnet-5-5`).
  - `ANTHROPIC_BASE_URL`: API base URL (default `https://api.anthropic.com`); only changed in tests to point at a local mock.
- **Smart allergen suggestions** (`lib/allergen-assist.ts` prompt, checks and keyword fallback, `app/api/allergen-assist/route.ts`, `lib/allergen-assist-client.ts`, `components/allergen-suggest.tsx`): the Suggest Allergens button in the ingredient allergen editor and Suggest For Unreviewed Ingredients on the dish card send one ingredient or a batch of up to 20 and get proposed allergen and diet ids with a one-sentence reason each. Same pattern as the step tidy: signed-in and allow-listed only, reply must be JSON that passes strict checks (known ids, no duplicates, short plain reasons, no dashes), otherwise the keyword check in `lib/allergens.ts` answers in the same shape with a `fallback` reason (`allergenNote` words it). It only proposes: nothing is saved until a person accepts, accepting never sets `allergens_reviewed`, and the toast can undo it. Uses `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL` as above, plus optional `ALLERGEN_ASSIST_MODEL` (default `claude-sonnet-5-5`, same as the step tidy); no key values anywhere in the repo.
- **Research This Drink** (`lib/research-drink.ts` prompt, strict checks and the call, `app/api/research-drink/route.ts`, `lib/research-drink-client.ts`, `components/editor/research-drink.tsx`): only for NEW cocktails and mocktails. `cost_menu_items.research_status` (null never offered, `offered`, `done`, `skipped`) is set to `offered` only by the New Recipe flow for those two categories (Duplicate and Save As New Dish start null, so do all ~90 existing drinks); the recipe page shows the Research This Drink card while it is `offered`. One tap sends the SAVED recipe to the route, which uses Anthropic's server-side `web_search_20250305` tool (max 4 searches, 50 s budget inside `maxDuration = 60`) and files up to 6 manager-only Research Notes through `store.addResearchNotes` (skips titles the drink already has, max 12 notes per drink). It never edits a recipe, and a source URL is kept only if the search tool itself returned it, so the model cannot invent a link. `research_status` and the note inserts go straight to the database, never through the editor draft. Same auth and fallback-reason pattern as the step tidy (no built-in fallback: failure keeps the card with a plain reason). Uses `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL` as above, plus optional `RESEARCH_DRINK_MODEL` (default `claude-sonnet-5-5`). Web search must be enabled for the Anthropic organisation in the Console privacy settings and costs $10 per 1,000 searches plus tokens. No key values anywhere in the repo. Troy reviews existing drinks by asking for it manually; there is no button for that.
- **Two people, one record** (`lib/edit-conflict.ts`, `lib/fresh-record.ts`, `lib/conflict-view.ts`, `components/editor/conflict-sheet.tsx`): Save in the recipe editor first reads the dish or prep and its lines fresh from the database, then does a three-way check by CONTENT (base = last loaded or saved, mine = draft, theirs = fresh), never by timestamps. Nothing changed underneath: saves as before. Changes that do not clash: saves the merge (a line someone else added survives) and toasts who. A clash (same field or same line changed differently, or removed on one side and edited on the other): nothing is written, the "Changed While You Were Editing" sheet offers Keep Mine / Use Theirs / Cancel. A failed fresh read is a failed save (Not Saved, Retry), never a blind write. Migration `20261004230000_edit_stamps.sql` adds `updated_by` (the signed-in email) beside `updated_at` on `cost_menu_items` and `cost_preps`, stamped by triggers; a change to a recipe line also stamps its parent. The app works before it is applied (no name, "Someone"). The field update is guarded by the fresh `updated_at` (`.eq`), so two saves in the same second cannot both pass; **recipe lines are NOT atomic** (a delete plus an upsert), so a small race window remains. Any new code that writes a recipe's lines or fields from a draft must go through this check, not `updateItem` / `saveLines` directly.
- **Active, not Delete** (`lib/active.ts`, `lib/record-usage.ts`, `components/active-parts.tsx`): every record with an `active` flag (menu items, preps, ingredients, tap beers, gelato serves, supplier deals; offers use `status = retired`) has ONE visible `ActiveToggle` ("Active", same sub line everywhere; tap beers say "On Tap"; cocktails and mocktails keep "Show On Drinks Station", same flag). Inactive means: hidden from lists unless "Show Inactive (n)" is on (rows dim with an "Inactive" tag), left out of GP averages, Today alerts, price suggestions, stations, specials and the allergen/menu labels grid, not offered by smart-add or pickers, demoted in search. An inactive record that active recipes still use keeps costing normally (never break a recipe's cost) and the page says so; turning one off asks first with the impact. Delete is the rare path: every Delete opens `DeleteRecordSheet` (impact first; used by anything = Delete not available, only "Make Inactive Instead"; unused = "Make Inactive Instead (Recommended)" then "Delete Permanently"). Never add a bare delete button or a raw delete call; a test enforces it. Alerts count an ingredient as "in use" only through ACTIVE recipes (`ingredientsInActiveUse`).
- **Trash and restore** (`/trash`, `lib/trash.ts`, `components/restore-sheet.tsx`, `restoreFromPlan` / `restoreDeleted` in `lib/store.tsx`): built on `cost_change_history`; nothing is ever purged by the app. A record is in Trash when its latest `delete` row on a restorable parent (`cost_menu_items`, `cost_preps`, `cost_beers`, `cost_gelato_serves`, `cost_offers`, `cost_ingredient_deals`) has a key that is no longer in the live table. Its lines are the child delete rows (`parent_table`/`parent_id` = the record) from 10 minutes before to 1 minute after the parent's delete; with transaction ids only the latest group counts, so a line removed in an ordinary save earlier is not pulled in. The parent-to-children registry (`RESTORABLE`) lives in `lib/trash.ts`. Restore shows the impact first (`planRestore`), then re-inserts the parent and its lines with their ORIGINAL ids through `insertRow`/`insertRows`, then refreshes the store. A name clash (menu items and preps unique on name + venue; beers and gelato serves on venue + name) or a missing record the parent points at (a tap beer's keg, a deal's ingredient) blocks the restore and writes nothing; a recipe line whose ingredient or prep is gone is listed in the sheet and left out while everything else comes back; if the parent insert fails no lines are written. Research Notes are deleted by the database with their dish or prep (cascade) and are not kept in history, so they do not come back (the sheet says so). Offer lines and specials that pointed at a deleted dish or beer were cleared by the database (set null) and are not re-linked.
- **Record History and Undo This Change** (`components/editor/record-history.tsx`, `lib/undo-change.ts`): a History group under Research Notes on dishes, drinks and preps lists the latest 10 events for the record and its recipe lines (Show More / Show Fewer). Undo never writes: `planUndo` works out the earlier values and they are loaded into the editor DRAFT (`setDraft` / `setLines`), so the normal Save bar, leave guard and conflict check apply. Field update: each changed field goes back to its old value (JSON columns whole). Line added: removed from the draft. Line removed: added back with its original id (not if its ingredient or prep is gone, and it says so). Line amount changed: old values put back. The record's own add or delete is informational (a delete is what Trash restores). A later change to the same field adds a "changed again" warning. No history yet, a failed fetch or a missing table all read "No history yet". Ingredients, beers and serves have no History group yet.
- **Gelato dietary labels** (`lib/gelato-labels.ts`, `components/editor/gelato-dietary.tsx`, `/gelato/dietary`, migration `20261005100000_gelato_dietary_labels.sql`, seed `supabase/seed-gelato-dietary-labels.sql` run by hand): a gelato flavour carries exactly the six labels on Troy's laminated sheet (Dairy Free, Vegan, Contains Egg, Contains Soy, Contains Nuts, Contains Gluten) instead of the generic Menu Labels group; the sheet is the master. `cost_preps.dietary_labels` NULL = Automatic (worked out from the ingredients, never stored, so new flavours fill themselves in), a non-null array = set by hand (the editor writes the full array into the DRAFT, so Save bar, leave guard and conflict check apply; Reset To Automatic writes null). The derivation is rules on ingredient NAMES (never flavour names): lib/allergens.ts keywords and ticks plus `GELATO_NAME_RULES` for the supplies they miss; a reviewed ingredient is taken at its ticks. Dairy Free and Vegan are claims, never made for an empty or unresolvable recipe. Almond milk and coconut count as nuts. `tests/gelato-labels.test.ts` pins the agreement with the sheet against `tests/fixtures/gelato-flavours.ts` (the live ingredient names, 5 Oct 2026): 121 of 132 cells; when ingredients or the sheet change, re-copy the fixture and re-read the missed list rather than loosening rules. The printable sheet's layout, fixed rows (Plain Cones) and rule lines (All sorbets, All vegan gelatos) are constants in `DIETARY_SHEET`. The Menu Labels grid is untouched.

## Design rules (Apple HIG thinking)
- One dark Caloundra Food Precinct theme. Page titles in the `display` (Bebas) class; venue fonts only in venue logos. Accents: Drift #B3E3F2, Chiobu #C6102E (text #FF5A70), Greedy #F26345, Gelato #ED8CCD, precinct sand #D9C3A0.
- Title Case for buttons, tabs, segments, titles and section headers ("Menu Items", "Update Price"); sentence case for helper text.
- **No hidden controls**: no dropdown pills, no controls tucked in menus when a visible row works. One round + (AddButton) top right to add; no floating buttons.
- Show impact before saving (e.g. Update Price previews which dishes fall below target). One-tap "Set $X" fixes are always undoable.
- `.anim-page` must stay opacity-only (a transform traps fixed children). Tailwind opacity modifiers don't work on CSS-var colours — use the `--*-soft` tokens.
- Users: owners/managers on phones, head chefs in the kitchen, office/bookkeeper and exec chef on desktop. Tables on desktop, rows on phones.
